AZURE2 Core Structure

AZURE2 stays a C++ code built for speed. This page describes it the way a physicist would: as the three lines it computes, the modules that compute each symbol, and the one direction in which they depend on each other. Python is used only to set projects up, for the web UI and for your own scripts.

The gradient is the same three lines differentiated: ∂m/∂θ = s · K · ∂O/∂θ and ∂m/∂ν from K(ν). No new machinery.

Who may use whom

Why this is not spaghetti

Interconnection is not the problem; every physics code is connected. Spaghetti is three specific things: dependencies that go in circles, state that several parts write, and effects you cannot see from the call. The structure removes all three.

  • Dependencies point one way. physics uses nothing; experiment uses physics (masses, kinematics); inference uses both; front ends use inference and io. Each module is its own library in the build and may link only the ones below it, so a wrong dependency does not compile.
  • One feedback loop. Only the fitter writes θ and ν. During an evaluation everything else is read-only, so no two parts can step on each other, in any number of threads.
  • Each module computes one symbol. To know what changes m, read one line of the equation.

What today's code does instead

A data point (EPoint) holds the measurement, its channel tables, its results and pointers to other points; a host point writes into the points mapped onto it; every thread copies the whole data set and then shares parts of it back. That is a cycle through shared, writable state, and it is where the races and the memory growth of the last three months came from.

Where the speed comes from

  • One collision-matrix solve per grid energy, used by every reaction, angle and target window.
  • Channel functions per (α, l, E), not per Jπ × channel.
  • Levels and channels as arrays (E[λ], γ[λ, c]) per Jπ block.
  • The apparatus as one sparse matrix product per measurement.

What runs when

The top row is built once per fit stage and never written again. The bottom row depends only on θ and ν. The fitter is the only thing that feeds back.

Coulomb functions: pycoulomb

The physics module takes its Coulomb functions from your pycoulomb C++ library directly, pinned to a tagged version. One implementation then serves AZURE2 and pycoulomb's Python users, and it replaces external/coul, CoulFunc, CoulFuncCache and the hybrid-potential code (pycoulomb's Numerov hybrid).

Its several methods (coul, coulsm, coulfg, GSL) become an identity test: they must agree where their domains overlap.

Identity checks, no data needed

  • Coulomb functions against mpmath; Wronskian F′G − FG′ = 1
  • U unitary when only elastic channels are open; optical theorem
  • One narrow isolated level reproduces the Breit–Wigner area
  • A constant σ survives every response operator; Gaussian ∘ Gaussian is Gaussian
  • Brune ↔ formal ↔ Park round trip; gradient equals finite differences; results independent of thread count

During the migration

  • The old engine computes golden outputs for T1–T3; the new one must match them, or the difference must be explained by the quadrature estimate.
  • The ~96 current test folders stay as extra oracles until the phase that replaces their code is merged, then retire.
  • A benchmark (time and peak memory) runs on T2 at 1 and 8 threads.

Reading the nuclear-data libraries

pyazr's readers take records from local copies of the libraries when a project is set up; the engine core then reads only the project. No web service at run time, so a fit runs offline and on a cluster, and gives the same answer next year. Each reader turns a library record into the same project objects a .azr line produces, and attaches its provenance: library, file, record, library version and checksum. Downloading or updating a library is a separate command, not part of a run.

A project can name records instead of copying them (for example a segment from an EXFOR subentry, level seeds from ENSDF), with the library locations in one user setting. Stopping and straggling in AZURE2

Today AZURE2 takes stopping either as a formula typed by the user or from ERYA, which ships SRIM's coefficient file SRIM2013.xml (SRIM's non-commercial terms, inside a GPL code). Straggling is c·√ΔE or plain Bohr, without the low-energy correction and without propagation through the target. The plan replaces both with a module of AZURE2's own, built from published formulas and fitted to measured data, with a stated uncertainty that the fit can use.

Stopping

  • Material, a physical object: elements with stoichiometry, density, phase (solid or gas), and a composition profile in depth for implanted targets. Stoichiometry, density and profile can be nuisance parameters.
  • Electronic stopping: SRIM-2013's, for any ion in any element (Z = 1–92), solid or gas, ported to C++ from LunaSRIM with SRIM's data files, SRIM cited (decision of the PI, 2026-11-11). Its published accuracy (4 % for H and He ions, 6 % for heavier ions) is the stated uncertainty.
  • Any projectile: SRIM's own treatment (H, He, Li fits joined to Bethe; heavier ions scaled from helium with SRIM's effective charge).
  • Nuclear stopping: SRIM's pair-specific fit (ZBL reduced units).
  • Compounds: Bragg additivity with SRIM's phase factor and compound correction (a number the user gives).
  • Uncertainty used, not hidden: each table carries its evaluation uncertainty, which becomes the prior of a stopping-scale nuisance per material in the fit.

Straggling and the target

  • Energy-loss straggling: Bohr with Chu's low-energy correction and the charge-state term, in the empirical form of Yang, O'Connor and Wang (1991).
  • Propagation through the target: the width at depth x follows σ²(x) = S(E(x))² ∫ (dΩ²/dx′) / S(E(x′))² dx′ (Tschalär), so a wide spread shrinks or grows with the slope of the stopping as it should. Beam energy spread adds in quadrature at each depth.
  • Targets: layers with tilt, dead layers, implanted profiles, extended gas targets with pressure and temperature. The Target response builder turns all of this into weights on the nodes, rebuilt in milliseconds when a nuisance moves.
  • Your own numbers: a measured stopping table or formula for a material, with provenance, overrides the evaluation.
  • Tests: identities (a thin layer loses S·Δx; σ tends to Bohr at high energy; weights conserve probability; Bragg sum of elements equals the compound without correction) and validation (the evaluation against the IAEA measurements per ion and element, residuals within the stated uncertainty, committed as a table). T2 uses a solid, an implanted and a gas target.
  • Licence: published formulas plus coefficients we fit ourselves are GPL-clean. Before any third-party table is shipped (NIST PSTAR/ASTAR, the IAEA database itself), its redistribution terms are checked; until then they are used for fitting and comparison only.

Order inside this module: material and target geometry, ZBL nuclear stopping, Bethe with corrections, straggling with propagation and user tables first; then the fitted low-energy evaluation for protons and α in the elements and gases used in nuclear astrophysics; then compounds and heavier ions.

Angular-momentum conventions

Today the conventions are implicit: channels are coupled as (l, s) with channel spin s = j1 + j2 (the 2S and 2L fields of the .azr file), with Lane–Thomas phases, and the signs of fitted widths, external-capture amplitudes and Coulomb phases follow from the code rather than from a stated rule. Comparing with other codes (rmfit, SAMMY, GNDS evaluations, Descouvemont-type calculations) then means guessing signs.

In this structure the fix is small. The core computes in one internal convention, written down once in the docs. A Convention record in the System states what a project's parameters mean, and the Parameterization stage converts them at the boundary:

  • coupling scheme: channel spin (l, s) or jj (j = l + j1, then J = j + j2). The change is an orthogonal matrix of 6j symbols per (α, l, J) acting on the γ columns of a Jπ block: γ′ = γ · C.
  • coupling order j1 + j2 or j2 + j1: a sign (−1)j1+j2−s per channel.
  • phase conventions: il factors, the sign of reduced widths, Coulomb-phase reference, and E/M multipole phases of photon channels, each a diagonal of ±1 or a phase.

How hard. The conversion itself is a few hundred lines: 6j symbols, a sign table, and their derivatives for the gradient, all applied as one block matrix in the Parameterization stage. Nothing downstream changes, because amplitudes, coefficients and responses only ever see internal-convention γ.

Where the care goes. Interference signs. Between levels of one Jπ and between a level and external capture, the observable depends on relative signs, so the photon-channel phases and the EC amplitude phase must be pinned by tests, not by reading the code.

The test that makes it safe. Observables are invariant under a change of convention when the full set of channels of an (α, l, J) is present. So every test project is run in every supported convention, and the observables must agree to rounding while only the parameter values change. A missing channel in jj ↔ (l, s) recoupling is reported, not silently dropped.

What it buys. Parameters can be read from and written to other codes' conventions, translations to GNDS become a table instead of a skill, and the sign questions that keep coming up in evaluations get one answer.

pyazr and the web UI

pyazr: the core, in Python

  • One package, modules named like the core. project (load, edit, save, provenance), system (partitions, Jπ blocks as numpy arrays, conventions, parameterization), data (measurements, apparatus, response previews), objective (value, gradient, residuals, Jacobian, terms, the named parameter vector), evaluate (observables at any E and θ, extrapolation, rates, decomposition), sources (AME, ENSDF, EXFOR, measured stopping), bands, plot.
  • Arrays without copies. Setup data are read-only numpy views of the core; an evaluation returns arrays.
  • No fitting framework. pyazr gives the objective with its gradient and Jacobian; fits and samplers are your scripts. The docs show short recipes for iminuit, scipy and emcee.
  • No physics in Python except reading the libraries and presenting results; any Python formula is tested against the core.
  • One command: pyazr ui, pyazr import exfor|ensdf, pyazr stopping (tables and plots from AZURE2's stopping module), pyazr libraries update (the only command that uses the network).
  • Installed with pip. Wheels for Linux, macOS and Windows carry the compiled core and the azure2 CLI. They replace the Qt installers.
  • pyazr 3.0. Today's azure2() session stays for one release as a shim that warns and maps onto the new objects.

Web UI: a small local web app

  • Local and offline. pyazr ui project.azr starts FastAPI and uvicorn (the pyazr[web] extra) and serves one static page with plotly.js copied in (the stack of your LunaSRIM web app, without depending on it); on a cluster, --host and an ssh tunnel.
  • A thin /api that maps one to one onto pyazr objects. The server and the browser hold no physics and parse no files.
  • Long jobs (fits, extrapolations, imports) run in worker processes, one engine per project, with progress and a stop button, and a limit on concurrent jobs.
  • The project is the state. Every edit goes through Project and is saved as .azr; undo is the project history; closing the browser loses nothing.
  • Tabs follow the physics. Project (files, libraries, provenance, conventions) · Nucleus (partitions, channels, Jπ blocks, levels, with ENSDF suggestions beside them) · Data (measurements, EXFOR import, frames, targets with their stopping and straggling, resolution, Doppler, shifts, normalizations, covariance) · Fit (parameters, priors, run, χ² per measurement, pulls, correlations) · Results (curves at any E and θ, S factor, rates with bands, decomposition) · THM only when the project enables it.
  • Tested without a browser: pytest on /api with T1–T3, plus a few browser smoke tests, and the Qt parity checklist before Qt is removed.
  • Later, maybe: a browser-only version (Pyodide), if the core compiles to WebAssembly.

Rules for CLAUDE.md

Shape

  • Modules use only the modules below them (figure 1). Each is its own library target, so a wrong include does not compile.
  • New physics goes in at one of the places in “Adding new physics” and changes one symbol of the three lines.
  • Data are arrays, indexed, not objects with pointers. Physics stages are functions.
  • The core computes in one stated angular-momentum and phase convention; conversions happen only at the Parameterization boundary.
  • One implementation of each formula and file format, in C++. A Python copy needs a test against it.
  • Front ends own no physics and no parsing.
  • No network access in the engine. Every imported number carries its provenance.

Performance and threads

  • Setup state is read-only after the stage starts; parallel code writes only its own slice or scratch.
  • No caches beyond the stage tables. A new cache needs a written reason, a complete key and a size test.
  • A perf change states time and peak memory on the T2 benchmark and passes TSan and ASan at 8 threads.

Tests and skills

  • Every feature appears in T1, T2 or T3 and has an identity check where one exists.
  • A reference value changes only with an independent reason written in the commit.
  • Skills link the docs, stay under 500 lines, carry no commit history, and follow the ten-skill set above: one skill per task.

Order of work

  1. Build T1–T3 and the identity checks; record golden outputs from today's engine; sanitizers and benchmark in CI; rewrite the skills into the ten-skill set; write the rules.
  2. System and Jπ blocks as arrays; channel functions per (α, l, E) from pycoulomb; the internal convention written down and the Convention record added.
  3. One objective with one list of terms.
  4. One project model: a single .azr parser and writer, plus the library readers (AME, ENSDF, EXFOR).
  5. Stopping and straggling module (next to the response operators): materials, nuclear and high-energy stopping, straggling with propagation, then the fitted low-energy evaluation; ERYA and SRIM2013.xml removed.
  6. Node set on Ex, amplitudes per node, coefficients B per reaction.
  7. Response operators, including shifts, THM and S-factor folds.
  8. Kernel without per-thread copies; remove mapping, clones and caches.
  9. pyazr 3.0 on the new binding: the modules above, wheels for three platforms, the old session as a shim.
  10. Web UI on pyazr 3.0 (a read-only project viewer can come right after step 4 to collect feedback); checked against the Qt parity checklist (docs/upgrade/qt_parity.md); then remove ERYA and numcmc from the tree (Qt is already out: decision 3).

Physics review notes

Points a referee would raise against the earlier drafts, and how this one handles them.

  • Elastic scattering is not a finite Legendre series. Rutherford scattering and Coulomb–nuclear interference are not. On keeps the nuclear amplitudes per (l, s, J); the kernel row carries the Coulomb amplitude fC(θ) at the point's angle. It stays linear.
  • Narrow resonances. The grid is planned from the current levels and resolves each width. Rates of narrow resonances add the analytic narrow-resonance term instead of relying on the grid alone.
  • Brune basis. Shift functions at Eλ move with θ. They are evaluated in the level-parameter step, a few per evaluation, not taken from the grid tables.
  • Spin–orbit in hybrid-potential channels makes the channel functions depend on j; those are indexed (α, l, j).
  • Ratios such as Ay fold numerator and denominator separately before dividing.
