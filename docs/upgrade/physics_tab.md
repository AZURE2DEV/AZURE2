# The Physics tab: what the engine gives the front ends

The Physics tab shows the quantities between the level parameters and the observables: the channel functions of a
pair, the R-matrix and collision matrix of one J^π group of the project on an energy grid, the poles of the level
scheme, the Trojan-horse (THM) parts of the entrance vertex and the apparatus kernels that fold a cross section into
a yield. An experimentalist needs them to see why a fit does what it does: which channel carries a resonance, where a
background pole sits, how strongly the penetrability suppresses a partial wave at the energies of the data, how much
of a THM spectrum is vertex and how much is the R-matrix. This note states, for every page, which engine function
gives each curve or map, its arguments with units and frames, whether it needs the project and a parameter vector,
and the interface the Qt tab (`gui/`) and the web page (`pyazr/ui`) call (section 7, exact). The PI's request of
2026-11-19: "a tab about physics, where the different R-matrix parts can be plotted, or THM parts, or collision
matrix poles finding with a heatmap"; the director's proposal of six pages was approved the same day.

Nothing here computes a number the engine does not already compute, except one diagnostic, det A⁻¹ (section 5.2),
which has its own unit test. No output of an existing run changes.

## 1. Two kinds of quantity

*Session-free* functions take physical numbers and need no project: the Sommerfeld parameter, the Coulomb functions,
P_l, S_l, φ_l of a pair given by its charges and masses, the Wigner limit, the THM plane-wave vertex. They are the
rows of the physics table (section 2), one row per function, evaluated element by element on arrays.

*Per-session* functions need the project: its pairs (masses, separation energies, radii), its J^π groups and their
channels, the options of the calculation (Brune, Park or the standard parametrization; the Coulomb table; a nuclear
potential of the hybrid model), and a parameter vector, either the project's start values or a parameter file
(`param.sav`), read as `AZURE2 --parameter-file` reads it. The front end opens a *session* of the saved project
(section 7.2): the engine sets up the levels and the data (or the extrapolations) as `AZURE2 calculate` would. The
set-up took 0.2 s for T3 and 5.5 s for T1, whose external-capture integrals were computed (measured 2026-11-19, one
thread, Coulomb table in use); every later call takes milliseconds (section 7.2).

## 2. The physics table in plain C++

The rows (name, one-line summary, doc, the library function called, the axis, the arguments with unit, kind, domain,
example and sweep, the returned fields with unit, and an adapter that converts the arguments and calls the library)
are `api/physics_table/src/PhysicsTable.cpp`, `BuildTable()`; the types are
`api/physics_table/include/azure2/physics_table/PhysicsTable.h` (`ArgSpec`, `OutSpec`, `PhysicsRow`, `CheckDomain`,
`EvaluateElement`). The target `azure2_physics_table` links `physics/`, `physics/transfer` and `experiment/` (for
`Frames.h`) and nothing above them: no pybind11, no Qt, no engine header. Two readers:

- the binding, `api/src/pybind_physics.cpp`: `pyazr.physics.<name>`, `pyazr.kinds()["physics"]`, the generated page
  `docs/source/user_guide/physics_functions.rst`, the web page's Physics tab (`GET /api/physics`);
- the facade, `api/front/src/FrontPhysics.cpp`: `front::PhysicsFunctions()`, `front::EvaluatePhysics()`.

The move (2026-11-19) changed no row: the page generated by `tools/gen_physics_docs.py` is byte for byte the page of
the commit before, `pyazr_physics_table` and check 41 pass unchanged (check 41 reads the rows from the new file). The
stopping table (five rows, SRIM-2013 through `stopping/`) moved the same way the same day:
`api/physics_table/src/StoppingTable.cpp` (`BuildStoppingTable()`, `EvaluateStoppingRow`), read by
`api/src/pybind_stopping.cpp` (`pyazr.stopping`, `pyazr.kinds()["stopping"]`) and the facade
(`front::StoppingFunctions()`, `EvaluateStopping()`); the binding's rows and values on 50 elements of every row for
three materials hash to the same SHA-256 as before the move.

## 3. Page "Channel functions"

For a pair (Z₁, Z₂, atomic masses m₁, m₂ in u) in orbital l at channel radius a_c (fm) and c.m. energy E_c (MeV) of
the pair, with ρ = k a_c and η the Sommerfeld parameter:

    P_l = ρ / (F_l² + G_l²),   S_l = ρ (F_l F_l′ + G_l G_l′) / (F_l² + G_l²),   φ_l = arg(G_l + i F_l)      (3.1)

| Curve | Session-free row (`PhysicsTable.cpp`) | Library function | Per session |
|---|---|---|---|
| F, F′, G, G′, σ_l vs ρ | `coulomb_waves` | `physics/coulomb/Coulomb.h: coulomb` | — |
| P_l vs E_c | `penetrability` | `physics/ChannelFunctions.h: penetrability` | `ChannelFunctions` series `P` |
| S_l vs E_c | `shift` | `ChannelFunctions.h: shift` | series `S` (below threshold the closed-channel S_l) |
| φ_l vs E_c | `hard_sphere_phase` | `ChannelFunctions.h: exp_minus_i_phi` | series `delta_hs` = −φ_l |
| dS_l/dE vs E_c | `shift_derivative` | `ChannelFunctions.h: channel_functions` | — |
| W_l(ρ) of a bound channel | `whittaker_wave` | `physics/coulomb/Whittaker.h: whittaker_scaled` | — |
| γ²_W, Γ_sp | `wigner_limit`, `single_particle_width` | `physics/Widths.h` | — |

The per-session values are the session's own: `AZUREAPI::GetCoulombFunctions` (`api/src/AZUREAPIChannelFunctions.cpp`),
the numbers pyazr's `Session.channel_functions` returns, with the Coulomb table when one is in use (F and G
interpolated to about 1 × 10⁻⁷ relative) and the Numerov solution of the hybrid model for a pair with a nuclear
potential. They differ from the session-free row only there; `api_front` checks P of T1's pair 1 against the row to
1 × 10⁻⁶. Web page: the row `channel_functions` of `pyazr/session_functions.py` (served since 2026-11-13).

## 4. Page "R-matrix of the project": one J^π group on an energy grid

For J group g (1-based, as `parameters.out` numbers the groups) and excitation energies E_x of the compound nucleus
(MeV), with each channel's c.m. energy E_c = E_x − (separation energy + excitation energy of its pair):

    (A⁻¹)_λμ = (E_λ − E_x) δ_λμ − Σ_c γ_λc γ_μc (S_c − B_c + i P_c)                                      (4.1)
    U_cc′ = Ω_c Ω_c′ (δ_cc′ + 2 i P_c^½ P_c′^½ γ_cᵀ A γ_c′),   Ω_c = exp(i(ω_c − φ_c)),   ω_c = σ_l − σ_0  (4.2)
    T_cc′ = exp(2 i ω_c) δ_cc′ − U_cc′                                                                     (4.3)
    U_c = (exp(2 i ω_c) − T_cc) / exp(2 i ω_c),   δ_c = arg(U_c)/2,   η_c = |U_c|                          (4.4)

(4.1) is the standard form; in Brune's and Park's parametrizations the level matrix is the one
`physics::fill_level_matrix` forms for them (shifts at the levels, B_c, Park's J_λλ). δ_c is in degrees, in (−90°,
90°], and in [0°, 180°) for identical particles: the engine's `phase_shift` data kind (`src/GenMatrixFunc.cpp`,
`physics/Observables.h: collision_from_t_matrix, phase_shift_degrees`), so a curve of this page and the program's
extrapolation of a phase shift are the same number (checked: `api_front`, T1's extrapolation `x3`, J = 1/2⁺, l = 0,
to 1 × 10⁻⁶ relative; measured 4.7 × 10⁻¹¹).

The engine function: `AZUREAPI::JpiBlockAllRWA(p, jgroup, E_x)` (`api/src/AZUREAPIBlockMatrices.cpp`; report
`api/include/JpiBlockReport.h`). It fills the session's level state at the vector p as `ObservedLevelRowsAllRWA`
does (`CompoundSystem::FillCompoundFromParams`, `CalcShiftFunctions`), gathers the level parameters as
`AMatrixFunc::FillLevelMatrix` gathers them, takes each channel's P, S, exp(−iφ) and exp(iω) from the stage's channel
rows (`ChannelTable::Compute`, with `ScatteringLength::ZeroEnergyShift` exactly at a threshold, as
`Site::CalcEDependentValues` does), and calls `physics::collision_matrix` (the level route; the engine's channel route
for blocks with fewer coupled channels than levels agrees to round-off). It is a new reader of these functions: no
evaluation path was edited.

| Curve | Series (facade) / key (pyazr `Session.jpi_block`) | Unit |
|---|---|---|
| P_c, S_c, E_c per channel | `P`, `S`, `E_c` / `channels[].P`, `.S`, `.E_c` | —, —, MeV |
| L_c − B_c as A⁻¹ reads it | `L_re`, `L_im` / `channels[].L_re`, `.L_im` | — |
| U_cc′ (c ≤ c′, open particle channels) | `U_re`, `U_im`, `U_abs` / `elements[]` | — |
| T_cc′ | `T_re`, `T_im` / `elements[]` | — |
| δ_c, η_c (Argand plot: U_re against U_im of the diagonal) | `delta`, `eta` / `phase_shifts[]` | deg, — |
| abs(A_λμ), λ ≤ μ | `A_abs` / `level_pairs[]` | MeV⁻¹ |
| det A⁻¹ | `det_re`, `det_im`, `log10_abs_det` | MeV^n |

A closed channel (E_c ≤ 0) and a photon or β channel have no U or T element (NaN). A photon channel enters A only
with R-matrix capture (`use_rmc`); its capture amplitude is not a channel function of this page (its penetrability
(E_γ/ħc)^(2L+1) is formed inside `Site::CalcEDependentValues` and is not called here, to keep one copy of it).
Eigenphases of a block with several open channels (the eigenvalues of U) are not given: physics/ has a real
symmetric eigensolver only (`SymmetricEigen.h`); a complex symmetric one is the missing piece, with a test of
U = Q exp(2iΔ) Qᵀ against mpmath.

Web page: the row `jpi_block` of `pyazr/session_functions.py` (axis `e_x`, arguments `jgroup` and the working x),
drawn by the Physics tab with no line of JavaScript (`pyazr/CLAUDE.md`, "A diagnostic of the session on a tab").

## 5. Page "Pole map"

### 5.1 The poles the engine knows

The physical (observed) energy E_x and the observed widths of each level, from the engine's own transformation
(`CompoundSystem::TransformOut`, the table `parameters.out` is written from): `AZUREAPI::ObservedLevelRowsAllRWA`
(`api/src/AZUREAPIReports.cpp`), ten numbers per channel of every level: J group, level, channel, E (MeV), the kind of
the observed value (width, ANC, static moment, β feeding), W (MeV, signed), the value as `<levels>` writes it (Γ in
eV, C in fm^-1/2), the P that W was formed with, μ (u), a (fm). In Brune's and Park's parametrizations E is the
level's energy of the vector; in the standard one it is the observed energy found by the engine's iteration, not the
formal E_λ. Facade: `PhysicsSession::Poles()` (`totalWidth` the sum of abs(W) over the channels whose kind is a width).
This is a list of real-axis resonance parameters, not the complex poles of U (5.3); for a narrow isolated level the
two agree to O(Γ/E_c).

### 5.2 A real-energy map

On the real axis the poles show where |det A⁻¹(E_x)| has its minima and where |U_cc′| and |A_λμ| peak. The map is the
series of section 4 as rows of a 2-D array, the energy as columns: rows = pairs of channels (|U_cc′|), or pairs of
levels (|A_λμ|), or J groups (log₁₀ |det A⁻¹| of each group, one `Block` call per group). The Qt page draws these
rows as a heatmap; the web page draws them as lines.

det A⁻¹ is `physics::level_matrix_determinant` (`physics/include/azure2/physics/LevelMatrixDeterminant.h`, Gaussian
elimination with partial pivoting on a copy of the matrix `fill_level_matrix` forms). It is a diagnostic only: the
engine's calculations factor A⁻¹ and solve (`LevelMatrixSolver.h`) and never form it. Test
`physics_level_matrix_determinant`: the 2 × 2 rule, the 3 × 3 cofactor expansion with a zero first pivot, a singular
matrix, and the one-level one-channel matrix, whose determinant is the Breit–Wigner denominator
E₁ − E − γ²(S − B + iP) (Lane and Thomas, Rev. Mod. Phys. 30 (1958) 257, section XII); a sign error in a row
exchange fails it at 1 × 10⁻¹⁴. `api_front` checks on T1 that the minimum of |det A⁻¹| over 2.2–2.5 MeV lies within
Γ = 33 keV of the 1/2⁺ level at E_x = 2.365 MeV.

### 5.3 The complex energy plane: not supported by the engine's routines

The poles of U are the zeros of det A⁻¹(E) continued to complex E, with L_c(E) = S_c + i P_c continued as
ρ H⁺′(η, ρ)/H⁺(η, ρ), H⁺ = G + iF, on the sheet Im k_c < 0 of each open channel. **The engine's routines take real
energy only**, so the complex-plane map is not built. The evidence, file by file:

1. `physics/coulomb/include/azure2/physics/coulomb/Coulomb.h`: `CoulombWaves coulomb(int l, double eta, double rho,
   Method)` and `coulomb_phase(int l, double eta)`; the header states "real Sommerfeld parameter eta ..., real
   rho = k r > 0", and the status `invalid_argument` covers ρ ≤ 0. The adaptors pass real numbers into the complex
   third-party routines: `src/method_coulcc.cpp` calls `coulcc(std::complex<double>(rho, 0.0),
   std::complex<double>(eta, 0.0), ...)`, `src/method_coulsm.cpp` makes `Coulomb_wave_functions_accurate(true, l,
   std::complex<double>(eta, 0.0))`. No test of `physics/tests/coulomb*_test.cpp` calls them at a complex argument.
2. `physics/include/azure2/physics/ChannelFunctions.h`: `eta`, `rho`, `penetrability`, `shift`, `exp_minus_i_phi`,
   `channel_functions` take `double E_MeV` and return real P and S separately; P is not analytic (it is the imaginary
   part of L on the real axis only).
3. `physics/include/azure2/physics/CollisionMatrix.h`: `fill_level_matrix(const LevelMatrixTables &, double E_MeV,
   ...)` and `collision_matrix(..., double E_MeV, ...)`; L_c − B_c enters as a complex number per channel, but
   computed by the caller at a real energy. The engine's callers (`CoulFunc`, `ChannelTable::Compute`, the Coulomb
   table `include/CoulombTable.h`, interpolating on a real grid) all take `double energy`.
4. The shift functions at the levels in Brune's and Park's forms (`CompoundSystem::CalcShiftFunctions`) are real
   functions of the real level energies; in a complex continuation they stay as they are (they are parameters), but
   the energy-dependent L_c(E) must be the continued one.

What it would need (a design for a later step, not code of tonight):

- *An adaptor* `coulomb_complex(int l, std::complex<double> eta, std::complex<double> rho)` in `physics/coulomb`
  over COULCC (`coulcc/`, Thompson and Barnett, Comput. Phys. Commun. 36 (1985) 363, written for complex η and ρ),
  returning H⁺, H⁺′ (mode 2 of COULCC) with its status. COULCC is bit-identical to the Fortran and accurate to
  4.4 × 10⁻¹⁶ in the Wronskian on the real axis (`physics/coulomb/README.md`); off the axis its accuracy is to be
  measured.
- *L_c on the second sheet*: k_c = (2μ E_c)^½/ħc with the branch Im k_c < 0 for each channel open at Re E_x (the
  resonance poles), η_c = Z₁Z₂e²μ/(ħ² k_c), L_c = ρ_c H⁺′/H⁺; a closed channel keeps the decaying branch (Im k_c > 0).
  A choice of sheet per channel is a choice of the map shown, and the page must say which.
- *A complex-energy level matrix*: `fill_level_matrix` with `E_MeV` complex (the diagonal E_λ − E); the formula is
  otherwise unchanged, so a template on the energy's type keeps one copy.
- *Checks*, in a `truth.py` with mpmath (`coulombf`, `coulombg` accept complex η and ρ): (i) H⁺ and H⁺′ of the
  adaptor against mpmath on a grid of complex ρ (|arg| up to 30°) and η for l = 0–4, the Wronskian
  H⁺′ H⁻ − H⁺ H⁻′ = 2i; (ii) a one-level one-channel case whose pole E_p solves E₁ − E − γ²(L(E) − B) = 0, found by
  mpmath's `findroot` and compared with the zero of the map; (iii) a two-level case of one J^π (two zeros, their
  repulsion), the same; (iv) the real axis limit: the map at Im E = 0⁻ equal to the real-energy determinant of 5.2.
  The validity region to state: |Im E| up to a few total widths of the levels shown and Re E_c above about 50 keV for
  charged channels, where COULCC's continued fractions converge; checked, not assumed.

Until then the page "Pole map" shows 5.1 and 5.2: the poles as points (E_x, Γ) and the real-energy map.

## 6. Pages not served by a single call yet

### 6.1 Decomposition (levels, interference, external capture)

The engine has no level/interference/external-capture decomposition. It exists as a pyazr procedure only:
`.claude/skills/azure2-calculate/scripts/decompose.py` and `pyazr/examples/decompose_cross_section.py`, four
evaluations at fixed parameters of one data set or extrapolation (`Session.evaluate`): *full*; *off* (one level's
free widths zeroed: the model without it); *only* (every other level's free widths zeroed, bound final states kept);
*bare* (every free width zeroed: hard sphere and external capture). Then full − off is what the level does (its
resonance and its interference), only − bare its bare resonance, and their difference the interference. The
"sample decompositions" of `src/DataOutputFiles.cpp` are another thing: the per-nucleus terms of a natural target.

Design for the facade (not built): `PhysicsSession::Decompose(record, level labels)` would hold no formula; it would
run the session's evaluation (`AZUREAPI::UpdateSegmentsAllRWA`, the model values of `calculated_segments`) at four
full vectors made from the session's by zeroing widths, as the script does through pyazr. What must be decided first:
(1) the vector: the script zeroes *free* widths only and lists fixed ones; the facade would zero every width of the
level in the full vector (fixed ones included), which differs from the script when a fixed width is non-zero; (2)
the external-capture amplitudes scale with the ANCs of the bound final states, which "bare" keeps (the script's
`--zero-bound` drops them); (3) a check: for an angle-integrated cross section, the pairwise interference
only{L,K} − only{L} − only{K} + bare of two levels of different J^π is zero to round-off (the script's own check), and
full = bare + Σ resonances + interference by construction. Web page: the script is not a row; a session row
`decompose` (a method of `Session` calling `evaluate`) would be the way to serve it there.

### 6.2 Apparatus (kernels, stopping, straggling)

*Stopping and straggling vs energy*, session-free: the five rows of the stopping table
(`api/physics_table/src/StoppingTable.cpp`: `stopping_power` in eV/(10¹⁵ atoms/cm²) with electronic, nuclear and
SRIM's relative uncertainty, `range` and `areal_density_between` in atoms/cm², `energy_after` and
`energy_straggling` in MeV (TRIM or Bohr straggling with Tschalär's propagation, the beam's spread carried through),
energies lab MeV of the projectile, SRIM-2013 with its citation, owed beside every plot). Facade:
`front::StoppingFunctions()`, `EvaluateStopping(name, formula, columns, ...)`, `StoppingCitation()` (section 7.1);
web page: `GET /api/stopping` (served since 2026-11-13). A target record's own stopping (a `stopping table` or
`formula` of the project, the stopping scale) is not reachable this way: it needs the session's `TargetStopping`
(`src/TargetStopping.cpp`) through a session call, not built.

*Kernel shapes* (Gaussian beam spread, beam profile, Doppler window, energy resolution, target integration, UDR): each
kernel of `experiment/include/azure2/experiment/Kernels.h` (`Kernels()`, rows `gaussian`, `beam_profile`,
`triangular`, `rectangular`, `target`, `doppler`, `udr`) is a fold of node values, templated on V; with
`V = LinearForm` it gives the exact weight of each node, the numbers the gradient reads. The shape of a record's
kernel at a point E₀ is those weights divided by the nodes' quadrature spacing, on the point's own nodes. What is
missing is a call that builds a data set's `KernelParameters` and `KernelPoint` outside a run
(`TargetEffect::KernelParametersFor`, `src/TargetSetup.cpp`): a session method `KernelShape(record, E0_lab)` returning
(E_cm nodes, weight density) would read the session's `WorkingCopy` effects and call the row's fold with `LinearForm`.
Its test: the Gaussian row's shape against the closed-form normal density, the rectangular one against a box, both
integrating to 1 (`AverageThinLimit`). Not built tonight.

### 6.3 THM

What `pyazr/session_thm.py` offers, through the facade (`PhysicsSession::ThmVertex`, `ThmLineshape`, `ThmDistortion`,
section 7.2), each on c.m. energies E of x + A (MeV) at the session's vector, from the same engine tables
(`WorkingCopy::ThmVertexTable`, `ThmLineshapeTable`, `ThmDistortionTable` through `AZUREAPI::GetThm*`):

- the entrance vertex: ⟨|M_l|²⟩ over the spectator-momentum window and |M_l|² at p_s = 0 per entrance channel and
  level (and the plane-wave |M_l(p)|² of `vertexModel=dw`); `reached` = 0 where the window does not reach E;
- the Coulomb line shape |N_C|² per exit pair and level (`lineshape=on`), ζ = η_sB − η₀ and the neglected η_sb;
- the distortion factor R(E) and its parts (`distortion=`).

The session-free THM rows are `thm_vertex_function` (the plane-wave surface vertex M_l(p)) and
`thm_full_form_factor`. The THM profile of the norms and backgrounds (`thm_experiments`, `thm_background`) is a
χ² evaluation and is not on this page. Half-off-shell against on-shell: the same J^π block in section 4 is the
on-shell R-matrix; the HOES cross section's other factors are the vertex (above) and the kinematic factor of the data
kind, which the engine applies per point and does not give as a function.

## 7. The interface for the front ends

All of it is in `api/front/include/azure2/front/Engine.h` (section "Physics"); `gui/` includes no other engine header.
Plain C++ types only. Energies in MeV, radii in fm, angles in degrees, phases in radians unless a field says degrees.
NaN marks a value that is not defined at that element; it is never a zero.

### 7.1 Session-free

```cpp
std::vector<PhysicsFunction> PhysicsFunctions();          // the rows, table order; no calculation (< 1 ms)
bool EvaluatePhysics(const std::string &name,
                     const std::vector<std::vector<double>> &arguments,  // one column per argument, row order
                     PhysicsValues &out, std::string &why);
std::string PhysicsStatusText(const std::string &name, int status);
std::vector<PhysicsFunction> StoppingFunctions();         // the stopping rows: arguments[0] is the formula ("text")
bool EvaluateStopping(const std::string &name, const std::string &formula,
                      const std::vector<std::vector<double>> &arguments,  // the NUMERIC arguments only
                      PhysicsValues &out, std::string &why);
std::string StoppingCitation();                            // SRIM's citation, shown under every stopping plot
```

- `PhysicsFunction`: `name`, `summary`, `doc`, `library`, `axis` (the argument a first plot runs over), `group`,
  `arguments` (`PhysicsArgument`: `name`, `unit`, `doc`, `kind` "real" / "integer" / "flag" / "choice", `domain` in
  words, `lower`, `upper` (±inf unbounded), `lowerOpen`, `upperOpen`, `choices`, `hasDefault` / `defaultValue`,
  `hasExample` / `example`, `hasSweep` / `sweepLower` / `sweepUpper` / `sweepLog`), `returns` (`name`, `unit`, `doc`).
  The same rows as `pyazr.kinds()["physics"]`. A form: one field per argument, its start value the default, else the
  example; a choice offers `choices` and sends the index; a flag sends 0 or 1.
- `EvaluatePhysics`: each column has n elements or 1 (a length-1 column is repeated). `out.values[k][i]` is return k at
  element i; `out.status[i]` 0 computed, k > 0 argument k outside its domain, −2 the arguments together outside it, −1
  not converged; NaN where the status is not 0. False only for an unknown name or columns of unequal lengths. The
  arithmetic is the row's adapter, bit for bit `pyazr.physics.<name>`. Cost: 1–50 µs per element; `coulomb_waves` with
  method `coulfg` or `coulcc` and `thm_full_form_factor` (a bound-state solve per element, about 1 ms) are the slow
  ones. A first plot of 200–400 points per line is instant.

### 7.2 Per session

```cpp
class PhysicsSession {                     // move-only; one thread at a time per object
  static bool Open(const std::string &projectFile, const std::string &parameterFile /* "" none */,
                   bool extrapolations, PhysicsSession &out, std::string &why);    // SLOW: the set-up (0.2-6 s)
  bool IsOpen() const;
  std::string Parametrization() const;     // "standard", "brune", "park"
  std::vector<PhysicsPair> Pairs() const;  // key, kind, z1, z2, m1, m2 (u), j1, j2, separation, excitation (MeV),
                                           // radius (fm), identical
  std::vector<PhysicsGroup> Groups() const;  // jgroup (1-based), J, parity, levels (in the R-matrix),
                                             // channels: channel, pair, radiation "P"/"E"/"M", l, s, radius
  std::vector<PhysicsPole> Poles();        // per level: jgroup, level, J, parity, energy (E_x, physical),
                                           // formalEnergy, totalWidth (MeV), widths[] {channel, pair, radiation, l, s,
                                           // kind "width"/"anc"/..., width W (MeV), value (eV or fm^-1/2), penetrability}
  bool ChannelFunctions(int pair, int l, double radius /* 0: channel radius */, int twoJ /* -1 */,
                        const std::vector<double> &eCm, PhysicsCurves &out, std::string &why);
  bool Block(int jgroup, const std::vector<double> &excitation, PhysicsCurves &out, std::string &why);
  std::vector<std::string> ThmExperiments() const;
  bool ThmVertex(const std::string &experiment, const std::vector<double> &energies, PhysicsCurves &, std::string &);
  bool ThmLineshape(...same...);           // runs one chi^2 evaluation first, as pyazr does
  bool ThmDistortion(...same...);          // SLOW: about 17 ms per energy (a DWBA per energy)
};
```

`PhysicsCurves`: `axis`, `axisUnit`, `axisValues` (the energies as given), `series` (each `PhysicsSeries`: `name`,
